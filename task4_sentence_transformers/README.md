# Семантический поиск по документации DataSphere

Ноутбук выполнен: 121 документ, 24 запроса, 3 модели эмбеддингов, TF-IDF и 9 экспериментов. Лучший вариант на этой выборке — **E5-small с окнами по 128 токенов: MRR@5 = 0,668, Recall@5 = 0,668**. У лучшего TF-IDF — 0,520 и 0,510 соответственно.

Учебное сравнение TF-IDF и трёх многоязычных моделей Sentence Transformers на русской технической документации. Весь код исследования находится в `work/semantic_search.ipynb`; исходный демонстрационный ноутбук сохранён отдельно.

## Запуск

Из корня репозитория:

```powershell
cd task4_sentence_transformers
docker compose up --build -d
```

Откройте [Jupyter](http://127.0.0.1:8891/?token=sentence_transformers), затем `work/semantic_search.ipynb`. Для повторного расчёта выполните **Kernel → Restart Kernel and Run All Cells**. Для просмотра сохранённых результатов выполнение не требуется.

Первый запуск требует интернета для сборки образа и загрузки весов. Корпус и запросы хранятся в `work/data/`, веса кэшируются в `work/.cache/` и не попадают в Git. Для следующего запуска достаточно `docker compose up -d`.

На компьютере, где выполнено исследование, образ уже собран: можно сразу запускать `docker compose up -d`. Для экономии места при сборке был использован готовый PyTorch из задания 3:

```powershell
docker compose build --build-arg TORCH_BASE=task3_pytorch_lstm-jupyter:latest
docker compose up -d
```

Этот вариант необязателен: обычная сборка создаёт базовый слой PyTorch самостоятельно. На этой машине WSL ограничена 3 ГБ RAM и 1 ГБ swap с согласия владельца; это локальная системная настройка, а не часть репозитория.

```powershell
docker compose down
```

Эта команда останавливает контейнер задания; ноутбук, данные и кэш остаются на диске.

В сравнении с исходным архивом: порт изменён с 8888 на 8891, публикация ограничена localhost; добавлены GPU, ограничение двух CPU и 2 ГБ RAM. Dockerfile использует Python 3.11, PyTorch с CUDA и фиксированные версии основных библиотек. `gensim` нужен только необязательному примеру GloVe из демонстрации и в исследовании не используется. Для компьютера без NVIDIA удалите `gpus: all` из Compose: ноутбук автоматически выберет CPU.

## Источники и ограничения

Корпус — опубликованная [русская документация Yandex DataSphere](https://yandex.cloud/ru/docs/datasphere/). Облачный аккаунт и платные API не нужны: поиск выполняется локально. Список страниц берётся из [официального оглавления](https://github.com/yandex-cloud/docs/blob/master/ru/datasphere/toc.yaml), текст — из опубликованной Markdown-версии страниц.

Исходная документация: Yandex, [CC BY 4.0](https://github.com/yandex-cloud/docs/blob/master/LICENSE). При подготовке корпуса удалены навигация, разметка ссылок и декоративные элементы, сохранены текст, команды и предупреждения. В каждой записи есть исходный адрес и дата получения. Документы могут описывать устаревшие возможности: корпус представляет сохранённый снимок документации.

Запросы и релевантность подготовлены и сверены с текстами AI-ассистентом. **Независимой проверки человеком нет**: формальное требование задания о ручной проверке человеком пока не выполнено. Разметка доступна для проверки в `work/data/queries.json`. Метрики на небольшой авторской выборке характеризуют это исследование, а не гарантированное качество на будущих запросах.

Исходная разметка сохранена в `queries.json`, уточнения — в `relevance_review.json`. После просмотра объединённой выдачи добавлено 12 соответствий и удалено 2. Для запроса о совместном ресурсе дополнительно просмотрены аналогичные инструкции по другим типам ресурсов. Уточнения применены ко всем методам; формулировки запросов и выдачи не менялись. Поэтому ранние результаты в отдельных ячейках отличаются от итоговой таблицы в ячейке 15. `retrieval_pool.json` сохраняет кандидатов для последующей проверки человеком.

Модели: [multilingual MiniLM](https://huggingface.co/sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2), [multilingual DistilUSE](https://huggingface.co/sentence-transformers/distiluse-base-multilingual-cased-v2), [multilingual E5 small](https://huggingface.co/intfloat/multilingual-e5-small). Все поддерживают русский язык; для E5 используются предусмотренные обучением префиксы `query: ` и `passage: `.

## Как устроено сравнение

Корпус содержит 121 самостоятельную страницу и 69 389 слов. Чанк — фрагмент страницы, а не дополнительный документ. Медианная длина страницы — 322 слова, максимальная — 3121. Короткие инструкции и длинные руководства представлены вместе. Команды из документации остаются текстом: ноутбук их не выполняет.

24 запроса охватывают GPU, окружение, данные, задания, инференс и доступ: по четыре на тему. Есть восемь прямых запросов, восемь перефразированных и восемь с дополнительным условием. Релевантность бинарная: документ должен содержать ответ по существу, простого совпадения темы недостаточно. Для каждого положительного соответствия в JSON записано обоснование. Запросы зафиксированы до сравнения моделей.

Сравниваются два способа разбиения:

- **Окна:** последовательные фрагменты с перекрытием примерно 20% слов.
- **Абзацы:** целые соседние абзацы упаковываются в один фрагмент без перекрытия; слишком длинный абзац разделяется на окна.

К каждому фрагменту добавляется начало заголовка страницы — до десяти слов. Итоговый вход ограничен 128 токенами **по каждому из трёх токенизаторов**, включая специальные токены и префикс E5. Очень длинные непрерывные последовательности символов предварительно разбиваются на части до 40 символов. Это защищает от единичных URL или идентификаторов, не помещающихся в окно. E5 умеет принимать более длинный вход, но здесь сравнение проводится при общем ограничении; вывод о её предельных возможностях из этого эксперимента сделать нельзя.

TF-IDF использует символьные n-граммы внутри слова длиной 3–5 (`char_wb`), логарифмическую частоту (`sublinear_tf=True`) и L2-нормализацию. Такой базовый метод учитывает части слов и менее чувствителен к русским окончаниям, чем точное совпадение целых слов. Словарь и IDF оцениваются только на документах, не на запросах.

Эмбеддинги нормализуются до единичной длины; скалярное произведение становится косинусным сходством. Для каждого документа берётся максимальная оценка его чанков. В выдаче пять **разных страниц**, а не пять фрагментов одной страницы. Такое агрегирование удобно для поиска локального ответа, но длинные страницы имеют больше шансов получить высокий максимум.

## Метрики для защиты

**MRR@5** отвечает на вопрос: «Насколько высоко появился первый полезный документ?» Для одного запроса это `1 / позиция` первого релевантного результата в первой пятёрке; если его нет, значение 0. Затем берётся среднее по запросам. Это основная метрика, потому что пользователю документации обычно нужен быстрый ответ.

**Recall@5** — доля размеченных релевантных страниц, найденных в первой пятёрке. Она дополняет MRR: первый правильный ответ может быть высоко, но остальные полезные страницы потеряны. Recall зависит от полноты разметки; поэтому при анализе нужно проверять и неразмеченные результаты выдачи.

У запроса q22 восемь релевантных страниц: общая инструкция и инструкции для конкретных ресурсов. Его максимальный Recall@5 равен 5/8, а не 1. MRR остаётся основной метрикой: для решения вопроса достаточно одной подходящей инструкции.

Время построения индекса измеряется отдельно от времени поиска. Скачивание и загрузка модели не входят в эти измерения. Скорость зависит от оборудования, фоновых программ и пакетной обработки; это локальный эксперимент, а не универсальный бенчмарк.

## Как объяснять код

1. **Библиотеки и ресурсы.** `Path` задаёт пути относительно папки ноутбука. `torch.set_num_threads(2)` ограничивает CPU; `torch.cuda.is_available()` выбирает GPU или CPU. На GPU выделение памяти PyTorch ограничено 35% видеопамяти. Это ограничение памяти, а не процент загрузки видеокарты.
2. **Корпус.** `requests.get` получает оглавление и страницы. `ThreadPoolExecutor(max_workers=3)` загружает три страницы одновременно. `clean_markdown` удаляет навигацию и служебную разметку. Фильтр отбрасывает страницы почти без текста; `drop_duplicates` удаляет полные дубликаты. Если JSON уже существует, используется сохранённый корпус без повторного скачивания.
3. **EDA.** `value_counts` показывает состав корпуса, `str.split().str.len()` считает слова, `describe` даёт квантили. Гистограмма показывает, насколько различается длина документов. Поиск фигурных скобок — диагностический признак, не ошибка: в руководстве по Query есть настоящие примеры Mustache/Jinja.
4. **Запросы.** Загружаются формулировки, сложность, тема и словарь `relevant`: ключ — идентификатор документа, значение — объяснение релевантности. Проверяется, что все размеченные документы существуют в корпусе. `crosstab` показывает баланс тем и типов запросов.
5. **Токенизация.** `AutoTokenizer` загружает правила токенизации каждой модели. Токен может быть частью слова, поэтому нельзя приравнивать 128 токенов к 128 словам. `model_text` добавляет E5-префикс. `fits` проверяет длину входа без обрезания.
6. **Чанки.** `split_window` двоичным поиском подбирает самый длинный допустимый фрагмент. При перекрытии следующее окно начинается чуть раньше конца предыдущего. `split_paragraphs` сохраняет абзацы, пока позволяет лимит. Финальная проверка считает токены каждого готового входа. Предупреждение токенизатора при проверке длинного кандидата не означает, что этот кандидат отправлен в модель: в модель попадают только проверенные короткие чанки.
7. **Ранжирование.** `argsort(-row)` упорядочивает сходство по убыванию. После сортировки `drop_duplicates('doc_id')` оставляет лучший чанк каждой страницы. `head(5)` формирует выдачу. `query_metrics` считает качество одного запроса, `evaluate` — всех запросов. Маленький пример с известным ответом проверяет смысл формул.
8. **TF-IDF.** `fit_transform` строит словарь и матрицу документов, `transform` кодирует запросы в том же словаре. `query_vectors @ matrix.T` вычисляет сходство запросов с чанками. `perf_counter` измеряет время.
9. **Модели эмбеддингов.** `SentenceTransformer` загружает готовую модель; обучения на нашей разметке нет. `encode` обрабатывает тексты пакетами по 16. `normalize_embeddings=True` нормализует векторы. На GPU веса и вычисления используют FP16 для экономии памяти, на CPU — FP32; для поиска полученные векторы переводятся в FP32. Один прогрев выполняется до замеров. После эксперимента модель удаляется и освобождается кэш GPU; результаты остаются в словаре `runs`.
10. **DistilUSE.** Повторяется тот же эксперимент, меняется только модель. Первые результаты MiniLM сохраняются.
11. **E5.** Повторяется сравнение на тех же чанках с обязательными префиксами для запросов и документов.
12. **Первая сводка.** `comparison_table` собирает качество и время. Объединяются топ-5 всех методов, чтобы проверить пропущенные релевантные страницы, а не автоматически считать каждый неразмеченный результат ошибкой.
13. **Дополнительная гипотеза.** Только для E5 увеличен лимит абзацев до 256 токенов. Получилось 755 чанков вместо 2010. Это отдельный эксперимент после основного сравнения при одинаковом лимите 128; старые результаты не заменены.
14. **Дополнение проверки.** Новые документы из выдачи E5-256 добавляются к списку кандидатов.
15. **Общая итоговая разметка.** Применяются сохранённые уточнения, затем заново вычисляются метрики всех вариантов. В CSV сохраняются общая таблица и результаты каждого запроса.
16. **Графики.** Сравниваются MRR/Recall и MRR отдельно для трёх типов запросов. Столбцы показывают средние по восьми запросам каждой группы.
17. **Разбор ошибок.** Выбираются лучшие варианты семантического поиска и TF-IDF, сравнивается RR каждого запроса. Показываются три выигрыша, три проигрыша и все запросы, для которых E5 не нашёл правильный документ в топ-5.
18. **Свой запрос.** Измените `search_query` и запустите ячейку после остальных. Выдача содержит заголовок, оценку, URL и фрагмент. Большой балл сходства не является вероятностью правильного ответа; особенно нельзя сравнивать абсолютные баллы разных моделей.

Если на защите спросят, почему здесь нет train/test split: мы сравниваем готовые модели поиска, а не обучаем классификатор. Документы составляют поисковый индекс, запросы с разметкой — оценочную выборку. Выбор победителя по этой же небольшой выборке делает её исследовательской; для независимой проверки понадобятся новые запросы с отдельной разметкой.

## Результаты

Расчёт: GTX 1650 4 ГБ, два потока CPU, FP16 для моделей на GPU. Время запроса — среднее на запрос при обработке пакета из 24 запросов, включая кодирование, поиск и объединение чанков. Это не задержка одиночного интерактивного запроса. Сбор корпуса и разбиение текста не входят во время индексации.

| Модель | Чанки | MRR@5 | Recall@5 | Индексация, с | На запрос в пакете, мс |
| --- | --- | ---: | ---: | ---: | ---: |
| E5-small | окна 128 | **0,668** | **0,668** | 39,50 | 11,78 |
| E5-small | абзацы 256 | 0,667 | 0,646 | 30,06 | 7,76 |
| E5-small | абзацы 128 | 0,608 | 0,609 | 36,55 | 7,95 |
| DistilUSE | абзацы 128 | 0,556 | 0,554 | 74,03 | 13,56 |
| MiniLM | окна 128 | 0,529 | 0,519 | 39,34 | 10,12 |
| MiniLM | абзацы 128 | 0,522 | 0,550 | 35,75 | 6,58 |
| TF-IDF | окна 128 | 0,520 | 0,510 | 0,86 | 1,50 |
| TF-IDF | абзацы 128 | 0,488 | 0,472 | 0,75 | 1,82 |
| DistilUSE | окна 128 | 0,465 | 0,589 | 77,28 | 13,08 |

По заранее выбранной основной метрике выигрывает E5 с окнами. Его преимущество над E5-256 — всего 0,0014 MRR: на 24 запросах нельзя объявлять такую разницу устойчивой. Для этой работы выбираем окна за чуть лучший MRR и Recall, а абзацы 256 рассматриваем как близкий по качеству вариант с меньшим индексом.

Абзацы не всегда лучше окон: DistilUSE выигрывает по MRR, MiniLM почти не меняется, E5 при лимите 128 проигрывает. Увеличение контекста E5 до 256 улучшает MRR относительно абзацев 128, но не даёт безусловного преимущества над окнами. Влияние разбиения следует измерять вместе с выбранной моделью.

У E5 с окнами MRR на прямых запросах — 1,000, на перефразированных — 0,442, на запросах с условием — 0,562. У TF-IDF с окнами соответственно 0,875, 0,260 и 0,425. Семантика помогает, но свободная формулировка и несколько условий остаются сложными. E5-256 лучше на перефразировках (0,562), однако хуже на прямых запросах (0,875).

### Примеры для объяснения преподавателю

| Запрос | Первый правильный результат TF-IDF | Первый правильный результат E5 с окнами | Что произошло |
| --- | --- | --- | --- |
| Коллеги нет в списке участников, как пригласить его? | нет в топ-5 | 1 | E5 нашёл инструкцию с приглашением по ссылке |
| Как добавить ресурс, опубликованный в сообществе? | нет в топ-5 | 1 | E5 различил использование общего ресурса и описание типов ресурсов |
| Закончилось место, где увеличить диск проекта? | нет в топ-5 | 2 | E5 нашёл изменение размера хранилища, TF-IDF — общие сведения о хранилищах |
| Постепенно переводить трафик на новую модель, сохраняя адрес | 5 | нет в топ-5 | E5 увлёкся словами о пользователях и вернул управление участниками вместо алиасов |
| Забрать файлы после обучения на свой компьютер | 2 | 3 | Оба метода нашли ответ, но TF-IDF поставил его выше |
| Отправить скрипт с автоматическим сбором зависимостей | 4 | 5 | E5 смешал установку библиотек и удалённый запуск задания |

Оба лучших метода не нашли в топ-5 инструкции для трёх запросов: добавление библиотеки для графиков с обновлением окружения, ежедневное неблокирующее обучение и приостановка сервиса с сохранением настроек. Это содержательные ошибки: общая близость темы не гарантирует выполнение всех условий запроса. Например, удаление ноды не эквивалентно приостановке с сохранением настроек.

### Что рекомендовать по результатам

Для этого корпуса разумная отправная точка — E5-small, нормализованные векторы и окна с перекрытием. Если важнее компактный индекс и свободные перефразировки, стоит рассмотреть E5 с абзацами 256. TF-IDF остаётся быстрым и дешёвым базовым вариантом, особенно для запросов с точными терминами. DistilUSE здесь медленнее и уступает E5; MiniLM не дал достаточного выигрыша, чтобы выбрать его вместо E5.

Более сложная модель сама по себе не исправляет неоднозначный запрос, плохую разметку или потерянное при разбиении условие. Следующий шаг перед реальным использованием — человеческая проверка релевантности и независимые пользовательские запросы. Дообучение, генерация ответов, векторная БД и веб-приложение в это задание не добавлялись.
