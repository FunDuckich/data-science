# Задание 6. Извлечение именованных сущностей локальными LLM

Решение: [work/named_entity_recognition.ipynb](work/named_entity_recognition.ipynb). Исходная демонстрация преподавателя сохранена отдельно.

## Запуск

Из этой папки выполнить `docker compose up --build -d`. Открыть http://127.0.0.1:8893/?token=local_llm_ollama и ноутбук решения. Первая загрузка модели занимает время. По завершении сохранить ноутбук и выполнить `docker compose down`. Именованный том с моделями сохраняется. Сервис `ollama-pull`, завершившийся с кодом 0, означает успешную загрузку модели; это нормальное состояние, а не падение контейнера.

Нужны Docker Desktop с WSL и NVIDIA GPU. Для запуска без NVIDIA убрать `gpus: all` у сервиса Ollama. Вызовы выполняются по одному, без параллельной загрузки нескольких моделей. Ключ облачного API для решения не требуется.

## Облачная альтернатива

Условия проверены 9 ноября 2026 года. Это оценка возможности использования, а не эксперимент с облачным API.

Groq предоставляет бесплатные вызовы GPT-OSS 20B: опубликованы ограничения 30 запросов/мин, 1000 запросов/сутки, 8000 токенов/мин и 200000 токенов/сутки. Фактические квоты зависят от аккаунта. Источник: [лимиты Groq](https://console.groq.com/docs/rate-limits).

У этой модели поддерживается строгая JSON Schema: [Structured Outputs](https://console.groq.com/docs/structured-outputs). Платный стандартный тариф — $0.075 за миллион входных токенов и $0.30 за миллион выходных: [модели и цены](https://console.groq.com/docs/models).

При оценочных 500 входных и 100 выходных токенах на предложение 100 запросов потребуют 50000 входных и 10000 выходных токенов. Стоимость — около $0.00675 без налогов и дополнительных затрат. Бесплатный запуск укладывается в суточные квоты; ограничение по токенам даёт оценку не менее 7.5 минут, по запросам — 3.34 минуты. Реальное время зависит от задержек сервиса и фактического числа токенов, включая рассуждения. Это расчёт по предположению, а не измерение.

OpenRouter предлагает бесплатные варианты с ограничением 20 запросов/мин и 50 запросов/сутки без пополнения; поэтому 100 отдельных запросов потребуют двух суточных квот. После покупки кредитов повышается суточный лимит, но это уже требует предварительной оплаты. Источник: [бесплатные модели](https://openrouter.ai/collections/free-models/). При 20 запросах/мин один только лимит частоты даёт примерно 5 минут на 100 запросов, но без пополнения раньше сработает суточный лимит. Время платного маршрута нельзя вывести только из цены: оно зависит от провайдера, его очереди и скорости генерации. Для воспроизводимого сравнения следует фиксировать модель и провайдера, а не использовать автоматический выбор бесплатной модели.

OpenRouter поддерживает JSON Schema через `response_format`, но только для совместимых моделей и маршрутов. Нельзя считать поддержку гарантированной у любой бесплатной модели; перед выбором нужно проверить доступные параметры провайдера. Источник: [Structured Outputs OpenRouter](https://openrouter.ai/docs/guides/features/structured-outputs).

Groq по умолчанию не сохраняет содержимое обычных запросов, но допускает временное хранение для расследования ошибок и злоупотреблений; доступны настройки Zero Data Retention. См. [обработку данных](https://console.groq.com/docs/your-data). В OpenRouter дополнительно действуют правила конкретного провайдера: [политики хранения](https://openrouter.ai/docs/guides/privacy/provider-logging). Поддержка JSON Schema также зависит от модели и провайдера.

Облако удобно для редких запусков без подходящей видеокарты. Локальная модель позволяет работать без отправки текстов внешнему сервису и без квот API, но требует памяти и времени на загрузку и вычисления. Бесплатный тариф и корректный JSON не гарантируют качество NER.

Для платного GPT-OSS 20B страница OpenRouter на дату проверки показывает стартовые цены $0.004 / $0.017 за миллион входных/выходных токенов: [тариф модели](https://openrouter.ai/openai/gpt-oss-20b/pricing). При том же предположении 50000/10000 токенов нижняя оценка составляет $0.00037. Это рекламируемый стартовый тариф, а не гарантия цены любого маршрута: выбранный провайдер, режим, рассуждения и комиссии могут изменить сумму. Стоимость токенов не равна минимальной сумме пополнения аккаунта. Перед реальным запуском нужно проверить конкретный маршрут и актуальные лимиты.

## Подготовка эталона

Из train-части `tner/conll2003` выбрано 100 предложений без повторения с seed=42. Первые 20 используются для анализа ошибок и единственного улучшения инструкции; остальные 80 — для основного сравнения. В evaluation содержатся 50 LOC, 18 MISC, 29 ORG и 37 PER.

Числовые метки взяты из [label.json исходного датасета](https://huggingface.co/datasets/tner/conll2003/blob/main/dataset/label.json). Их порядок отличается от других вариантов CoNLL-2003: нельзя просто подставить знакомую нумерацию. B- начинает сущность, I- продолжает её, O завершает. Повторные B- создают отдельные упоминания даже при одинаковом тексте. Преобразование проверяется на коротких примерах.

Текст собирается пробелами из исходных токенов. `inputs.json` содержит тексты без эталонных сущностей; `gold.json` хранится отдельно. Модель получает только инструкцию и текст.

## Как считаются метрики

Совпадение сущности требует точного текста и типа в пределах одного предложения. Повторы учитываются через Counter. Это оценка текстовых упоминаний, а не строгая оценка символьных границ: одинаковые упоминания в разных позициях одной строки не различаются. Регистр и написание не исправляются автоматически. Изменение типа даёт одновременно FP и FN. Счётчики суммируются по предложениям, затем рассчитываются micro precision, recall и F1.

Корректность схемы проверяется отдельно. Невалидный ответ считается пустой выдачей, поэтому все его эталонные сущности становятся FN; дополнительно снижается доля валидных ответов. Ошибка соединения не маскируется под результат модели: выполнение останавливается, уже сохранённые ответы остаются.

Для списка порядок проверяется сопоставлением фрагментов с их позициями в исходной строке, с учётом повторов. Доля правильного порядка считается только для ответов с двумя и более сущностями; рядом показано число таких случаев. У группировки по типам общего порядка нет, поэтому соответствующее поле не применяется. Правильный порядок не заменяет оценку правильности сущностей.

## Настройки эксперимента

Запросы отправляются последовательно. Температура 0, seed 42, контекст 2048 токена, ограничение ответа 512 токенов, два CPU-потока. Ollama использует доступную GPU; при нехватке видеопамяти часть вычислений может остаться на CPU. В памяти держится не больше одной модели. Это настройки воспроизводимости и умеренной нагрузки, а не гарантия побитово одинаковых ответов на любом оборудовании.

Запуск выполнен на Windows/WSL2 с NVIDIA GTX 1650 4 ГБ, Ollama 0.11.10, Python-клиентом ollama 0.6.1 и Pydantic 2.12.4. Qwen3 при запуске частично размещалась на CPU (Ollama показывала 9% CPU / 91% GPU), а Qwen2.5 полностью помещалась на GPU. Поэтому времена нельзя переносить на другие GPU, а разница отражает не только размер модели, но и размещение вычислений.

Первый прогрев модели не входит в замер. Время каждого последующего запроса включает локальный HTTP-вызов, обработку текста и генерацию ответа. Проверка Pydantic выполняется после остановки таймера. Среднее не является чистой скоростью генерации токенов, поскольку длины входов и ответов различаются.

Ответы сохраняются после каждого предложения в `work/results/*.json`. Повторное выполнение использует уже сохранённые ответы с той же моделью, инструкцией, схемой и настройками. Чтобы провести новый замер, нужно предварительно переместить соответствующий файл результатов; иначе таблица показывает время исходного запуска.

## Два формата Structured Output

В первом формате объект `entities` содержит четыре списка строк: PER, LOC, ORG и MISC. Даже пустые списки обязательны. Во втором `entities` — список объектов с полями `text` и `type`; тип ограничен четырьмя допустимыми значениями. Лишние поля запрещены в обеих схемах.

Схема передаётся в параметр `format` Ollama, а полученная строка дополнительно проверяется через `model_validate_json`. Это обеспечивает проверку структуры, но не доказывает, что названия найдены правильно. Модель может вернуть полностью валидный JSON и при этом пропустить имя, выдумать название или перепутать организацию и место. Именно поэтому качество извлечения оценивается отдельно.

Источник: [Structured Outputs в Ollama](https://docs.ollama.com/capabilities/structured-outputs).

## Что показал исходный опыт на development

Исходная краткая инструкция оставляла MISC слишком широким. В первых 20 предложениях модель относила к сущностям даты, числа, обычные товары, слова «abuses», «amnesty» и даже местоимение. JSON при этом был корректным. Это пример того, почему одной проверки схемы недостаточно.

В спортивных новостях модель путала клубы и города: West Bromwich должен быть ORG в контексте матча, а не LOC. Полное название Lokomotiv Nizhny Novgorod нельзя одновременно выдавать как клуб и отдельно как входящий в него город. Национальности European и Saudis относятся к MISC; превращение European в Europe нарушает и точное копирование текста.

Единственное уточнение инструкции ограничивает MISC именованными категориями CoNLL, исключает даты, числа и обычные слова, требует цельные названия без вложенных повторов и уточняет спортивный контекст. Готовые правильные ответы на evaluation в инструкцию не добавляются. Исходная инструкция и её результаты остаются отдельным экспериментом.

### Что показывают графики

Первый график сравнивает precision, recall и F1: улучшение инструкции в основном убирает лишние срабатывания. Второй показывает выигрыш меньшей модели по времени, но не доказывает её пригодность при низком качестве. Третий разделяет F1 по типам и раскрывает то, что скрывает общий показатель: PER и LOC заметно проще MISC.

### Почему MISC сложнее

У Qwen3 со списком F1 по типам: PER 0.8000, LOC 0.8000, ORG 0.6538, MISC 0.1569. Из 18 эталонных MISC найдено только 4, ещё 29 предсказаний этого типа оказались лишними. MISC объединяет разнородные случаи, включая национальности и некоторые собственные названия; модель продолжает ошибочно добавлять годы и обычные словосочетания.

В примере с Brazilian и Antonio Kandir модель находит эталонные сущности, но добавляет `1997` и `federal budget`. В предложении про Slovak Interpol она сливает национальность и организацию в одну ORG-сущность, теряя точные границы. В тексте про Urdu-speaking Moslems разбивает единую сущность и добавляет `1947`.

Сам эталон тоже содержит спорные случаи: `disarmament-China` отмечено как единая MISC-сущность, а `Partition` — LOC. Мы не исправляем разметку по ответам модели. Эти случаи показывают ограничение exact match: даже лингвистически разумный ответ может расходиться с соглашениями или особенностями корпуса.

### Как читать таблицу ошибок

`type_errors` — совпавший текст с неверным типом после удаления правильных совпадений. Каждая такая ошибка даёт и FP, и FN. `omissions` — оставшиеся FN, `extra_mentions` — оставшиеся FP. Эти величины нельзя дополнительно складывать с FN/FP: это разложение тех же ошибок.

`hallucinations` считает выданные фрагменты, которых нет в исходном предложении как отдельных текстовых фрагментов. Это более узкая величина, чем FP: слово может присутствовать в тексте, но не быть сущностью. У Qwen3 со списком таких фрагментов на evaluation нет, но FP всё равно 50. У Qwen2.5 с группировкой их 38: например, к футбольному счёту добавлены Germany и United Kingdom, которых во входе нет.
