## Запуск

Нужны запущенный Docker Desktop в режиме Linux containers и Python 3.11 или новее. На Windows используется WSL 2. Spark, Java, Jupyter и библиотеки ML уже находятся в Docker-образе. Загрузчик данных использует только стандартную библиотеку Python.

### Первый запуск из репозитория

```powershell
git clone git@github.com:FunDuckich/data-science.git
cd data-science/task1_pyspark_ml
python download_data.py
docker compose up -d --wait --wait-timeout 360
```

| Строка / аргумент | Что делает |
| --- | --- |
| `git clone ...` | Скачивает репозиторий по SSH; нужен GitHub SSH-ключ. Вместо SSH можно использовать HTTPS-адрес репозитория. |
| `cd ...` | Переходит в папку задания с Compose-файлом. |
| `python download_data.py` | Скачивает датасет с Kaggle, проверяет ZIP, извлекает CSV и сохраняет SHA-256. |
| `docker compose up` | Создаёт и запускает сервис; при необходимости скачивает образ. |
| `-d` | Запускает контейнер в фоне. |
| `--wait` | Ждёт успешной проверки готовности Jupyter. |
| `--wait-timeout 360` | Ограничивает ожидание готовности шестью минутами; это не лимит обучения. |

Открыть **http://127.0.0.1:8888/?token=pyspark_ml**, затем `work/fraud_detection.ipynb`.

Для просмотра достаточно открыть ноутбук: результаты сохранены. Для повторного выполнения сначала сохранить изменения, затем выбрать **Kernel → Restart Kernel and Run All Cells**, дождаться завершения и нажать **Ctrl+S**. Новые численные выводы формирует кодовая ячейка 13. Последний текстовый раздел с разбором завершённого эксперимента описывает сохранённый прогон.

После работы выполнить из папки задания:

```powershell
docker compose down
```

Это остановит и удалит контейнер и сеть проекта. Файлы в `work/` останутся на компьютере.

На компьютере, где работа уже лежит в `G:\data-science`:

```powershell
cd G:\data-science\task1_pyspark_ml

```

Если Kaggle требует вход, скачать `creditcard.csv` с [официальной страницы](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud) и положить в `work/data/`. CSV размером около 151 МБ в Git не включён.

### Автоматическое выполнение

Из PowerShell в папке задания:

```powershell
.\run.ps1 -Profile full
```

Скрипт загружает данные, если их нет, запускает контейнер, выполняет ноутбук, сохраняет HTML и результаты, затем вызывает `docker compose down` в `finally`. Результаты появляются в `work/artifacts/full/`; выполненный ноутбук также сохраняется в `work/fraud_detection.ipynb`.

Если PowerShell блокирует локальный скрипт, разрешить его только для отдельного процесса:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\run.ps1 -Profile full
```

Короткая техническая проверка:

```powershell
.\run.ps1 -Profile smoke
```

`full` использует весь датасет и полную сетку. `smoke` уменьшает данные и модели, сохраняется отдельно и не заменяет основной выполненный ноутбук. Его метрики не являются итоговыми.

При проблемах WSL с подключённым диском Windows предусмотрен вариант:

```powershell
.\run_isolated.ps1 -Profile full
```

Он копирует данные во внутренний том Docker, выполняет тот же код, экспортирует результаты в `work/` и останавливает контейнер. Прежние результаты сохраняются в `work/export_.../`, чтобы файлы двух моделей не смешались. Том сохраняется после `down` для восстановления при сбое экспорта. Override-файл использует тег `!override`; проверить поддержку установленным Compose можно так:

```powershell
docker compose -f docker-compose.yaml -f docker-compose.isolated.yaml config --quiet
```

Сохранённый полный прогон занял **22,4 минуты**. На другой машине время изменится. Spark использует до 6 потоков, Java-драйверу выделено 4 ГБ; Docker, Python и Windows требуют дополнительную память.

## Изменения Docker Compose

Сохранён исходный образ `quay.io/jupyter/pyspark-notebook:spark-3.5.3` и один контейнер. Отдельные master/worker не добавлялись. Spark работает в режиме **local[6]** при наличии шести CPU: используются партиции и Spark ML, но это не многомашинный кластер.

| Настройка | Было → стало; зачем |
| --- | --- |
| `version: '3.8'` | Удалено устаревшее поле версии Compose. |
| `image` | Тег → тег с SHA-256 digest; закреплён конкретный образ. |
| `ports` | `8888:8888` → `127.0.0.1:8888:8888`; доступ к Jupyter только с локального компьютера. |
| `volumes` | Добавлены два скрипта автоматизации с доступом только для чтения. Рабочая папка осталась. |
| `PYSPARK_SUBMIT_ARGS` | Добавлено `--driver-memory 4g pyspark-shell`; память Java-драйвера. |
| `PYTHONPATH` | Добавлены пути к PySpark/Py4J из образа для запуска Python без оболочки Jupyter. |
| `OMP_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, `MKL_NUM_THREADS` | Добавлено ограничение в 6 потоков для математических библиотек. |
| `restart` | `unless-stopped` → `no`; контейнер не перезапускается автоматически после сбоя. |
| `healthcheck` | Добавлена проверка HTTP API Jupyter для `up --wait`. |

Имя контейнера, токен `pyspark_ml`, включение JupyterLab и `extra_hosts` сохранены. WSL обновлялся отдельно на компьютере из-за аварий службы; это не изменение Compose, скрипты репозитория WSL не обновляют.

## Рассказ для защиты

> Я решаю задачу бинарной классификации транзакций. В датасете 284 807 операций и только 492 мошеннические. Accuracy почти бесполезна: постоянный ответ «не мошенничество» уже выглядит точным. Для ранжирования использую PR-AUC, для рабочего порога — precision, recall и F1.
>
> Разделил данные по времени: ранние 60% для обучения, следующие 20% для выбора семейства и порога, последние 20% для независимого теста. Группы одинаковых транзакций не пересекают части и CV-фолды. Внутри раннего периода CV стратифицирована по группам, но не является rolling-window CV; перенос во времени проверяют более поздние validation и test.
>
> В Pipeline входят медианы пропусков, log1p суммы, сборка вектора и модель. Для LR добавлена стандартизация. Весь Pipeline обучается внутри CV, чтобы обработка не видела удержанный фолд. Сравнил LR, RF и GBT: 28 конфигураций, 84 обучения по фолдам и финальное обучение лучших вариантов на train.
>
> На validation выбран Random Forest: 200 деревьев, глубина 10, без повышенного веса fraud. Порог 0,350264 выбран по F1 на validation. На test обнаружены 54 из 75 мошеннических операций, 21 пропущена, ложных тревог 8. Precision — 87,1%, recall — 72%, F1 — 0,7883, AP — 0,7962.
>
> Для сравнения библиотек обучил две логистические регрессии на одинаковых 100 000 строках и согласовал регуляризацию. Качество почти совпало, sklearn быстрее на этом локальном объёме. Это не вывод о скорости на распределённом кластере.
>
> Сохранил весь Pipeline с обработкой и порогом. В отдельном процессе загрузил его: все 56 961 предсказание совпали, максимальное расхождение оценок равно нулю. Проверил вход без метки, обучающих весов и с пропуском признака.

Порядок показа: распределение классов → разбиение → `make_pipeline` → `CrossValidator` → validation → матрица ошибок test → Spark/sklearn → проверка загрузки.

### Вопросы преподавателя

| Вопрос | Ответ |
| --- | --- |
| Зачем validation, если названы train/test? | Для выбора решений. Подбор порога на test лишил бы его независимости. |
| Почему время, а не randomSplit? | Реальная модель предсказывает будущие операции. Хронология проверяет перенос в следующий период. |
| Почему Time не признак? | Это секунды от начала записи, а не час суток. Здесь он задаёт хронологию; его переносимость ограничена. |
| Что такое V1–V28? | Готовые PCA-компоненты, исходные признаки скрыты. Я не обучал PCA и не могу проверить её исходный протокол. |
| Почему дубликаты не удалены? | Без идентификаторов не доказано, что это ошибки. Их кратность сохранена, а одинаковые признаки сгруппированы при разделении. |
| Зачем Imputer без пропусков? | Чтобы сохраняемый Pipeline умел обрабатывать новые данные с пропусками; это отдельно проверено. |
| Зачем log1p? | Снижает асимметрию больших сумм, определён при нуле. |
| Estimator и Transformer? | Estimator обучается через `fit` и возвращает Transformer. Transformer применяет `transform`. PipelineModel содержит обученные этапы. |
| Зачем весь Pipeline в CV? | Иначе медианы/scaler могли бы увидеть удержанный фолд и вызвать утечку. |
| Как учтён дисбаланс? | Групповая стратификация фолдов, подбор весов 1/10 и порога. Финальные метрики считаются без весов. |
| RF и GBT? | RF усредняет деревья с элементами случайности; GBT последовательно добавляет деревья, исправляя ошибки текущего ансамбля. |
| Почему RF? | Максимальная validation PR-AUC: 0,7665 против 0,7153 у LR и 0,6191 у GBT. |
| Почему F1? | Стоимость ошибок неизвестна. F1 — учебный компромисс, а не оптимальная политика банка. |
| Precision и recall? | Precision = TP/(TP+FP), доля верных тревог. Recall = TP/(TP+FN), доля обнаруженного мошенничества. |
| F1? | `2TP/(2TP+FP+FN)`, гармоническое среднее precision и recall. |
| AP и PR-AUC? | AP суммирует прирост recall с весами precision, общая PR-AUC здесь интегрируется трапециями. Они показаны отдельно. |
| Почему не ROC-AUC? | При редком fraud PR-метрики нагляднее отражают качество тревог. ROC-AUC показана дополнительно. |
| Почему на test лучше порог 0,5? | Настройка на validation не гарантирует улучшения в будущем. У RF F1 при 0,5 — 0,8217, при выбранном пороге — 0,7883: одна дополнительная верная тревога и семь ложных. Менять решение по test нельзя. |
| Контрольная LR получила AP выше RF — почему не заменить? | Это отдельный эксперимент библиотек. Выбор задним числом по test нарушит протокол; малое различие не доказывает превосходства. |
| Почему `C=1/(n*regParam)`? | Согласован коэффициент штрафа в усреднённой функции потерь; одинаковые численные C и regParam не эквивалентны. |
| Почему есть pandas? | Spark обучает модели и агрегирует данные. В pandas передаются небольшие сводки, ограниченная EDA-выборка и до 100 тысяч строк для оценки/sklearn. Не все метрики здесь безгранично распределённые. |
| Lazy evaluation? | `filter`, `select`, `transform` строят план. `count`, `collect`, `write` запускают вычисления. Время скоринга измеряется с action. |
| Persist/unpersist? | Кэширование и освобождение партиций; MEMORY_AND_DISK разрешает часть кэша хранить на диске. |
| Что показывает bootstrap? | Неопределённость метрик при повторной выборке групп в наблюдаемом периоде; будущий дрейф и переобучение полностью не учитываются. |
| Можно внедрять в банк? | Нужны новые временные периоды, стоимость ошибок, калибровка и аудит признаков. Нет ID карт, данных всего за короткий период. |
| Это потоковый скоринг? | Нет: обучение и проверка пакетные, по CSV. Structured Streaming не реализован. |
| Где распределённость? | Spark DataFrame, партиции и Spark ML; фактически стенд локальный, без нескольких физических узлов. |
